### 1. `notes.py:264-266` `-0000` を日本時間と読んでいるが、RFC では UTC の意味で、ブラウザ側とも食い違う（実害は未確認）

- 何が: `parsedate_to_datetime` は `-0000` とオフセット無しのどちらも naive を返すので、今の直しでは両方とも `replace(tzinfo=JST)` になる。だが RFC 5322 の 3.3 節では、`-0000` は「時刻は UTC で、送り手の地域の時差は分からない」という意味。一方 Chromium と同じ V8 の `Date.parse` は `-0000` を UTC として読む
- 実測（`TZ=America/New_York` と `Asia/Tokyo` で同じ結果）:

  | 入力 | Python（直した後） | JS（`toIsoDate` → 日本時間） |
  |------|-------------------|-----------------------------|
  | `Wed, 28 Oct 2026 22:22:06 -0000` | `2026-10-28T22:22:06+09:00` | 10/29 07:22 |
  | `Wed, 28 Oct 2026 22:22:06 +0000` / `GMT` / `UT` | `2026-10-29T07:22:06+09:00` | 10/29 07:22 |
  | `Wed, 28 Oct 2026 22:22:06`（オフセット無し） | `2026-10-28T22:22:06+09:00` | ブラウザのローカル時刻（New_York では 10/29 11:22、Tokyo では 10/28 22:22） |

- 実行した機械の時刻に左右されない、という点は直っている（両方の `TZ` で同じ値）。食い違うのは `-0000` を「UTC」と「日本時間」のどちらと読むかで、Python 側だけが日本時間と読み、9 時間ずれる
- 今の NHK の RSS は `+0900` を出し、rss2json は ISO の形（JS の正規表現の側）で返すので、今は起きない。オフセット無しを日本時間と読むことの是非は、NHK の RSS なら筋が通るので指摘しない
